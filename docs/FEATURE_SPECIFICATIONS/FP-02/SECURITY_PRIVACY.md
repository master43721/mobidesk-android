# FP-02 Security and Privacy Requirements

**Version:** 0.2 · **Date:** 5 November 2026  
**Subordinate to:** MobiDesk PRD v1.2, SECURITY_THREAT_MODEL.md and approved amendments.

## 1. Objective

Show only the fully authenticated student's approved profile and one valid assigned Cloud PC. The client is untrusted. Connect availability is a usability affordance; broker/FP-06 is authoritative.

## 2. Data allowlist

| Data | UI | Rule |
|---|---|---|
| Student display name | Yes | Current student's RLS result only |
| College label | Optional | Approved profile field only |
| Safe Cloud PC label | Yes | FP-03-approved field only |
| Lifecycle/transport | Yes | Approved enums and reviewed wording |
| sampledAt/probe duration | Optional | No infrastructure detail |
| assignmentTag | No | Equality only in memory; never display/log/persist |
| requestId | No | Opaque diagnostic only if parent telemetry allows |
| User/roll/other-student IDs | No | Never render/log |
| VM ID/UUID/name/hostname/IP/port/Guac | No | Never target or expose |
| JWT/grant/guest credential | No | Never Compose/navigation/disk/log |
| Raw response/exception | No | Map to approved safe copy |

## 3. Identity and assignment

- Protected reads start only after FP-01 FULLY_AUTHENTICATED.
- Use current Supabase session/RLS; never accept caller-chosen subject.
- FP-03 owns exactly-one assignment resolution and authorization.
- Clear prior user state and cancel calls on sign-out, AUTH-01, session-generation change or invalidation.
- Only typed FP-03 Assigned produces a card; zero/multiple/inactive/unmapped fails closed.
- assignmentTag is opaque, equality-only and generated by the shared trusted assignment resolver. It is not a secret or authorization credential. Rotate on assignment revision; never persist or log.

## 4. API/routing boundary

FP-02 owns Android StatusRepository; FP-04 owns GET /v1/vm-status and probe. Send current Supabase access JWT over HTTPS. GET has no body, query, user selector or VM target. Response allowlist: lifecycle, rdpTransport, sampledAt, probeDurationMs, staleAfterSeconds, requestId and assignmentTag. No VM identity or route. No service-role key in APK. No student VM assignment or power controls.

## 5. Freshness and Connect safety

PRD.md §6 is the single normative Connect rule. Stale/missing/indeterminate status leaves Connect available only as a user action to request a fresh check when identity/assignment are valid. The new sample must be fresh using monotonic receipt-age, have matching assignmentTag, lifecycle RUNNING and RDP_NEGOTIATION_OK before FP-05 handoff. Fresh known-negative states disable Connect. Once any sample is stale, its former state is indeterminate and Connect is available as a fresh-check action. In-flight requests and cooldown disable it temporarily.

Timeout, 429, mismatch or failed refresh invalidates prior actionable readiness. Previous positive sample may be labelled stale but cannot authorize. FP-06/broker independently revalidates assignment/readiness at grant time.

## 6. Timeout, cancellation and rate limits

- 8-second cancellable client deadline; cancel on screen/session lifecycle change.
- Cancellation is not an error toast and never starts a retry loop.
- Honor non-negative Retry-After delta seconds and the safe retryAfterSeconds body value; use the larger valid delay.
- No automatic retry; user action only after cooldown.
- Local 2-second minimum refresh interval prevents duplicate calls.
- Fallback cooldown 2/4/8/16/30 seconds applies only when server retry metadata is unusable.

## 7. Monotonic time

Use Android SystemClock.elapsedRealtime() for age and cooldown. Never compare sampledAt to handset wall time for authorization. FP-04 returns a newly sampled observation for every successful request; do not use pre-request cached observations. Invalid timing is indeterminate and denies handoff.

## 8. Logs and telemetry

Allow only parent-approved stage, safe error code, outcome, elapsed duration and redacted correlation ID. Never log student identity, assignmentTag, JWT/Authorization, grant, password, VM routing, raw response, screen pixels or RDP payload.

## 9. Threat controls

| Threat | Control |
|---|---|
| Stale Ready view | New request on every Connect; monotonic age; broker recheck |
| Status for different VM than card | Shared assignmentTag, paired reload once, ASSIGN-02 on repeat mismatch |
| Multiple assignments | FP-03 typed singleton; no first-row selection |
| TCP port misread as ready | TCP_REACHABLE is distinct and never handoffs |
| Phone wall clock skew | Monotonic receipt-age only |
| Hung/abusive refresh | 8s timeout, cancellation, debounce, 429 cooldown |
| Late cross-account response | Session generation and cache clear |
| Backend detail leakage | DTO allowlist and exact safe copy |
| UI tampering | Broker/FP-06 revalidates independently |

## 10. Acceptance

Cross-student negatives, tag mismatch, timeout/429, stale/wall-clock-jump, no-selector and sensitive-field scans pass. No private field or credential appears in UI/log/state. Broker authorization is independent of UI.
